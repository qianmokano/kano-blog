刚拿到一台 VPS 时，我通常不会立刻部署服务，而是先完成系统更新、普通用户、SSH、防火墙和备份入口等基础工作。下面以 Ubuntu 24.04 为例，整理一套可以逐项验证的初始化流程。

> 本文整理自我的 Notion 笔记，并参考了 [Ubuntu Server](https://documentation.ubuntu.com/server/how-to/security/openssh-server/)、[Docker Engine](https://docs.docker.com/engine/install/ubuntu/) 等官方文档。修改 SSH 和防火墙前，请保留当前会话，并确认云服务商提供网页控制台或救援模式。原始讨论见 [LINUX DO](https://linux.do/t/topic/817769)。

## 开始之前

准备好服务商提供的服务器 IP、`root` 初始密码，以及一个准备长期使用的域名。如果服务商支持安全组，还要确认它没有提前拦截 SSH。

第一次连接服务器：

```bash
ssh root@server_ip
```

首次连接时，SSH 会询问是否信任主机指纹。最好在服务商控制台核对指纹后再确认，而不是无条件输入 `yes`。

所有高风险操作都遵循三个原则：

1. 不要关闭当前 SSH 会话。
2. 每改一项配置，先验证，再从新终端测试连接。
3. 新连接确认可用后，才继续收紧旧的登录方式。

## 1. 更新系统

先刷新软件包索引并安装更新：

```bash
apt update
apt upgrade -y
```

如果更新包含内核、OpenSSL 或 systemd，可以在完成后重启：

```bash
reboot
```

等待服务器重新上线，再重新连接。不要在未确认 SSH 能重连时直接进入后面的配置。

## 2. 创建日常管理用户

长期使用 `root` 登录会放大误操作和凭据泄露的风险。创建一个普通用户，并按需通过 `sudo` 提权：

```bash
adduser kano
usermod -aG sudo kano
```

把 `kano` 换成自己的用户名。然后切换过去，确认提权正常：

```bash
su - kano
sudo whoami
```

输出应为 `root`。从这里开始，除非特别说明，命令都以这个普通用户执行。

## 3. 配置 SSH 密钥

SSH 密钥通常比可被猜测或复用的密码更适合作为日常登录凭据。先在自己的电脑上生成密钥；如果已经有合适的密钥，可以跳过生成步骤。

```bash
ssh-keygen -t ed25519 -a 100
```

为私钥设置口令，然后把公钥复制到服务器的新用户：

```bash
ssh-copy-id kano@server_ip
```

如果本机没有 `ssh-copy-id`，也可以查看公钥并手动放进服务器的 `~/.ssh/authorized_keys`：

```bash
cat ~/.ssh/id_ed25519.pub
```

服务器上的目录和文件权限应当足够严格：

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys
```

现在打开一个新终端，验证密钥登录：

```bash
ssh kano@server_ip
```

只有这一步成功后，才可以禁用密码和 `root` 登录。

## 4. 启用 UFW 防火墙

Ubuntu 默认提供 UFW。先设置默认策略，再明确放行当前使用的 SSH 服务：

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow OpenSSH
sudo ufw enable
sudo ufw status verbose
```

启用后不要退出当前会话，先从另一个终端再次连接。如果连接失败，可以利用仍然打开的旧会话检查规则。

后续部署网站时再放行 HTTP 和 HTTPS：

```bash
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
```

不需要的端口不要因为“以后可能会用”而提前开放。

### 要不要修改 SSH 端口？

修改默认的 22 端口只能减少自动扫描产生的噪音，不能代替密钥登录、防火墙和 Fail2ban。Ubuntu 24.04 的 OpenSSH 还使用 systemd socket activation，端口变更比修改一行配置更容易出错。因此，没有明确需求时保留 22 端口是完全合理的。

如果确实需要修改，先在防火墙和云服务商安全组中放行新端口，验证 SSH 配置，并在新终端测试成功后再删除旧规则。不要先关闭 22 端口再尝试连接。

## 5. 收紧 SSH 登录

Ubuntu 支持在 `/etc/ssh/sshd_config.d/` 中添加配置片段。使用文件名前缀 `00-`，可以让规则在常见的 `50-cloud-init.conf` 之前生效：

```bash
sudo nano /etc/ssh/sshd_config.d/00-hardening.conf
```

写入：

```text
PermitRootLogin no
PubkeyAuthentication yes
PasswordAuthentication no
KbdInteractiveAuthentication no
```

先检查语法，再查看 SSH 最终采用的配置：

```bash
sudo sshd -t
sudo sshd -T | grep -E 'permitrootlogin|pubkeyauthentication|passwordauthentication|kbdinteractiveauthentication'
```

确认输出符合预期后重启服务：

```bash
sudo systemctl restart ssh
```

保持当前会话不动，用另一个终端再次执行：

```bash
ssh kano@server_ip
```

最后确认 `root` 和密码登录已被拒绝。若验证失败，使用尚未关闭的会话修正配置；若会话已经断开，则通过服务商的网页控制台恢复。

## 6. 安装 Fail2ban

密钥登录已经挡住了多数密码猜测，但 Fail2ban 仍可用于减少持续扫描带来的日志噪音和资源消耗。

```bash
sudo apt install fail2ban -y
sudo nano /etc/fail2ban/jail.d/sshd.local
```

写入一个简单的 SSH 规则：

```ini
[sshd]
enabled = true
backend = systemd
port = ssh
maxretry = 5
findtime = 10m
bantime = 1h
```

启动并检查状态：

```bash
sudo systemctl enable --now fail2ban
sudo fail2ban-client status
sudo fail2ban-client status sshd
```

如果修改过 SSH 端口，`port` 也要改成实际端口。不要把永久封禁当作默认策略，以免把自己的动态 IP 长期挡在门外。

## 7. 设置时区和自动安全更新

正确的时区能让系统日志、任务调度和故障排查更直观：

```bash
sudo timedatectl set-timezone Asia/Shanghai
timedatectl
```

安装自动安全更新：

```bash
sudo apt install unattended-upgrades -y
sudo dpkg-reconfigure --priority=low unattended-upgrades
```

自动更新不能替代维护。仍然要定期查看是否有需要重启的服务或内核：

```bash
test -f /var/run/reboot-required && cat /var/run/reboot-required
```

## 8. 安装 Docker 和 Docker Compose

生产环境建议使用 Docker 的官方 APT 仓库，而不是方便但不可审查地执行在线安装脚本。先清理可能冲突的发行版软件包：

```bash
for pkg in docker.io docker-doc docker-compose docker-compose-v2 podman-docker containerd runc; do
  sudo apt remove "$pkg"
done
```

添加 Docker 官方仓库：

```bash
sudo apt update
sudo apt install ca-certificates curl -y
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
```

```bash
echo \
  "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu \
  $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}") stable" | \
  sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

sudo apt update
sudo apt install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin -y
```

验证安装：

```bash
sudo docker run --rm hello-world
docker compose version
```

如果希望普通用户无需 `sudo` 使用 Docker，可以加入 `docker` 组：

```bash
sudo usermod -aG docker "$USER"
```

重新登录后生效。注意：能访问 Docker daemon 的用户基本等同于拥有 `root` 权限，不要把不受信任的账号加入这个组。

### Docker 与 UFW 的关系

Docker 会自行创建防火墙规则。将容器端口发布到宿主机时，流量可能不会按直觉经过 UFW 的普通规则。因此，不能仅凭 `ufw status` 判断容器端口是否安全。

我的做法是：只向公网发布真正需要的 80 和 443；数据库、Portainer 等服务加入内部 Docker 网络，由反向代理通过容器名访问。更复杂的访问控制应放在 `DOCKER-USER` 链或云服务商的安全组中，具体可参考 [Docker 官方防火墙文档](https://docs.docker.com/engine/network/packet-filtering-firewalls/)。

## 9. 部署 Nginx Proxy Manager

[Nginx Proxy Manager（NPM）](https://nginxproxymanager.com/guide/)提供了一个可视化反向代理界面，适合在一台 VPS 上管理多个小型服务。先创建目录和共享网络：

```bash
mkdir -p ~/docker/npm
cd ~/docker/npm
docker network create proxy
```

创建 `compose.yml`：

```yaml
services:
  npm:
    image: jc21/nginx-proxy-manager:2.15.1
    container_name: npm
    restart: unless-stopped
    ports:
      - '80:80'
      - '127.0.0.1:8181:81'
      - '443:443'
    environment:
      DISABLE_IPV6: 'true'
    volumes:
      - ./data:/data
      - ./letsencrypt:/etc/letsencrypt
    networks:
      - proxy

networks:
  proxy:
    external: true
```

启动服务：

```bash
docker compose up -d
docker compose ps
docker compose logs --tail=100
```

管理端口 81 没有直接暴露到公网，而是映射到了服务器本机的 `8181`。在自己的电脑上建立 SSH 隧道：

```bash
ssh -L 8181:127.0.0.1:8181 kano@server_ip
```

然后访问 `http://127.0.0.1:8181`。按照 NPM 当前界面的提示完成首次登录，并立即修改默认邮箱和密码。

### 绑定域名和证书

在 DNS 服务商处添加 A 记录，把域名指向服务器 IPv4；只有服务器确实配置了可用的 IPv6 时才添加 AAAA 记录。DNS 生效后，在 NPM 中创建 Proxy Host：

- Domain Names：准备访问的域名，例如 `app.example.com`
- Scheme：上游容器实际使用的协议
- Forward Hostname：共享网络里的容器服务名
- Forward Port：容器内部监听的端口

再申请 Let's Encrypt 证书并开启 Force SSL。通配符证书通常需要 DNS Challenge，以及 DNS 服务商提供的最小权限 API Token；不要使用拥有完整账户权限的主密钥。

## 10. 部署 Portainer

Portainer 可以管理 Docker 容器，但挂载 `/var/run/docker.sock` 意味着它拥有接近宿主机 `root` 的能力。必须使用强密码、及时更新，并避免直接公开管理端口。

```bash
mkdir -p ~/docker/portainer
cd ~/docker/portainer
```

创建 `compose.yml`：

```yaml
services:
  portainer:
    image: portainer/portainer-ce:lts
    container_name: portainer
    restart: unless-stopped
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
      - ./portainer_data:/data
    networks:
      - proxy

networks:
  proxy:
    external: true
```

启动：

```bash
docker compose up -d
docker compose ps
```

因为 NPM 和 Portainer 都加入了 `proxy` 网络，所以 NPM 可以直接使用稳定的容器名访问它：

- Forward Hostname：`portainer`
- Forward Port：`9000`
- Scheme：`http`

不需要查询并写死 `172.x.x.x` 形式的容器 IP；容器重建后 IP 可能变化，而 Docker 内部 DNS 会继续解析服务名。

同样的方式也适用于其他 Web 服务：让它们加入 `proxy` 网络，不向宿主机发布后台端口，再通过 NPM 提供 HTTPS 入口。

## 11. 收尾检查

完成后，我会逐项确认：

- 普通用户可以通过 SSH 密钥登录
- `root`、密码和键盘交互登录已被拒绝
- UFW 只开放当前需要的端口
- Fail2ban 正常监控 SSH
- `apt` 没有遗留的重要安全更新
- Docker 容器没有意外发布数据库或管理端口
- NPM 和 Portainer 的默认凭据已修改
- DNS、HTTPS 和证书续期工作正常
- 服务配置和持久化数据有异地备份

可以用下面几条命令做快速检查：

```bash
sudo ss -tulpn
sudo ufw status verbose
sudo fail2ban-client status sshd
docker ps --format 'table {{.Names}}\t{{.Ports}}\t{{.Status}}'
```

最后，不要忘记在云服务商控制台做一次可恢复的快照，并实际验证备份能否还原。安全初始化不是“一次配置、永久有效”，而是后续更新、最小暴露和可恢复性维护的起点。
